## Scope slicing

The design groups live sync into M2, but the editor UI is rewritten in M3. To keep the two milestones file-disjoint and parallelizable:

- **M2 owns the backend:** host sessions, watcher, SSE, MCP server, CLI commands, agent skill, packaging. It does not edit `packages/editor`.
- **M3 owns the editor:** state architecture, canvas interactions, thumbnails/sorter, inspector, history, shortcuts, and the live-sync/autosave/conflict UI that consumes M2's SSE API.

This preserves every M2 requirement; the live-sync UI ships one milestone later, with the backend available for it.

## Dependency graph

```
M1 (done)
 ├─ M2 backend ────────────────┐
 │    ├─ M5A export renderer ──┤
 │    └─ M5B packaging/CI ─────┤
 └─ M3 editor foundation ──────┼─ M3 live sync (needs M2 SSE)
      └─ M4 PowerPoint features─┴─ M5C visual/security/a11y ─ M5 release
```

- **M4** depends on M3's state/selection/history foundation.
- **M5A (PDF/PNG renderer)** depends on M2's host API and CLI but not on M4 features; it can run parallel with M4.
- **M5B (packaging, docs, CI)** depends on M2 packaging and can run parallel with M4.
- **M5C (visual round-trip, security, a11y, final acceptance)** depends on M3 + M4 + M5A.
- Publishing remains deferred until M5 is complete and the user explicitly authorizes a remote push or npm publish.

## Concurrency waves

| Wave | Lane A | Lane B | Lane C |
|---|---|---|---|
| 1 | M2 tasks 1→6 sequential | M3 tasks 1→7 sequential | — |
| 2 | M2 tasks 7→8 (skill, packaging) | M3 task 8 (live sync, after M2 SSE) then M4 tasks 1→5 | M5A export renderer |
| 3 | M5B docs/CI | M4 tasks 6→8 | M5C visual/security/a11y |
| 4 | Final acceptance, merge, release prep | — | — |

Two implementation agents may run concurrently **only** in different worktrees and only when their file sets are disjoint. The controller reviews each task before dispatching the next task in that lane. Never run two implementation agents against the same worktree.

## Dependency decisions (explicit)

- **MCP:** `packages/mcp` uses the official `@modelcontextprotocol/sdk` (`^1.32.1`) with `zod` for tool schemas. Both are dependencies of the published `htmlppt` package and are bundled by tsup. Rationale: protocol correctness and real-agent interoperability outweigh a hand-written JSON-RPC loop.
- **Editor tests:** add `jsdom` as a dev dependency for geometry/snapping/rich-text unit tests (the test framework names jsdom).
- **Export:** add `playwright-core` (`^1.64.1`) in M5 for system Chromium PDF/PNG rendering (the design specifies it).
- No telemetry, no remote service calls at runtime.

## Global constraints for all remaining milestones

- Node >= 20, ESM, TypeScript strict. UI copy Traditional Chinese; code/docs/CLI/errors English.
- No retries, skips, or mocks of host/filesystem/Chromium in tests. Real processes and real files.
- The HTML file is the source of truth. Every write is serialized per file and atomic (temp + rename), with hash/revision conflict detection.
- No editor artifacts in saved or exported HTML. Scripts never execute in the editor.
- Host binds to 127.0.0.1, requires a per-session token, checks Origin, and exposes only the opened deck, exports, and editor assets.
- Deterministic ids, diagnostics, serialization, and geometry math.
- Local branches and local `--no-ff` merges only. No push, PR, npm publish, or remote repo creation without explicit user authorization.
- Every task ends with focused tests, a clean tree, and a commit. Every milestone ends with `npm run verify`, a whole-branch review, a merge to main, and a post-merge exit gate.

## Milestone definitions of done

- **M2:** `htmlppt open` writes a session; `stop` terminates it; the host pushes SSE revision events; `htmlppt outline` works; the MCP server passes stdio handshake and direct/host-attached tool tests; the skill and examples exist; `npm pack` smoke passes.
- **M3:** a user can select/transform/snap objects, see thumbnails, use the sorter and inspector, undo/redo, and see live external updates with a conflict banner; all editor E2E tests pass.
- **M4:** rich text, object insertion, tables, charts, notes/transitions/background, play/presenter view, and the remaining MCP asset/table/chart tools work end to end.
- **M5:** HTML/PDF/PNG export, visual round-trip, security/a11y tests, packaging/release docs, Ubuntu+Windows CI on Node 20/22, and the full acceptance suite pass.
